# Авто-подбор числа цветов + лесенка картонов на лету

Ветка `avto-podbor-cvetov`. План с аргументацией — по правилу `CLAUDE.md` «перед
исследовательской правкой — план в `docs/` и замер по `samples/`».

## Проблема

Пользователь задаёт в форме одно число — «не больше N цветов». `PaletteReducer.Reduce`
сворачивает палитру ровно до него, а после генерации выводится строка «Свёрнуто N
оттенков при лимите M: переназначено X %».

Мастер заметил эмпирику по этому проценту: **5–7 % — сюжет держится, выше 10–15 %
— сюжет заметно сыпется**. Правильное число цветов под конкретное панно приходится
искать вручную полной перегенерацией на каждую пробу. Приоритет мастера — не
максимальная точность, а «пренебречь там, где это не будет видно, чтобы не
заказывать лишние цвета, но не потерять сюжет».

## Почему процент модулей — не тот сигнал, по которому решать

Доля переназначенных модулей слепа к тому, **куда** попал сдвиг: клетка,
уехавшая в фоне, и клетка, уехавшая на клюве птицы, считаются одинаково. Это
эмпирика мастера, а не мерка для алгоритма.

`PaletteReducer.CheapestToDrop` уже считает нужное: суммарное перцептивное
смещение клеток сброшенного оттенка (расстояние каждой до её запасного варианта),
домноженное на `1 + 1.6·LargestComponentFraction` — насколько оттенок собран в
компактное несущее пятно. Это ровно та логика, по которой оттенок и выбирается на
выброс: дёшево — россыпь по фону, дорого — глаз, клюв, блик.

## Что делаем

### Лесенка стоимости

Жадный сброс в `PaletteReducer` **монотонно-вложенный**: свернуть до N, а потом
продолжить до N−1 — то же состояние, что свернуть сразу до N−1. Значит один
проход от `colorsBefore` вниз до пола даёт всю лесенку:

`[ число цветов → стоимость сброса этого шага (MarginalCost) → накопл. переназначено ]`

Новый `PaletteReducer.BuildLadder(...)` делает этот проход и на каждом шаге пишет
ступень со снимком `Indices` (клон). `Reduce` становится тонкой обёрткой над
`BuildLadder(..., floor: maxColors)` + возврат последней ступени — поведение и
ранний выход при `colorsBefore <= maxColors` сохранены, существующие тесты
`PaletteReducerTests` / `ReductionCostTests` не трогаются.

### Поиск колена

Абсолютная величина стоимости зависит от размера панно и числа тессер, поэтому
единый порог — снова «подгонка под gull.jpg». Вместо порога —
**предельная стоимость на каждый следующий сброшенный оттенок**: пока роняем
дешёвые (фон), кривая почти плоская; на первом несущем оттенке она резко идёт
вверх. Останавливаемся на изломе — это самонастройка под конкретное панно.

`ReductionLadder.Knee(int ceiling)`: идём от большого числа цветов вниз (дешёвые
сбросы первыми), ведём медиану `MarginalCost` уже пройденных ступеней; колено —
первый шаг, где `MarginalCost > KneeFactor · медиана`, при ≥3 набранных
ступенях. Возврат — число цветов ДО дорогого сброса, зажатое в
`[max(4, пол), ceiling]`. Колено не найдено (плавная кривая) → возвращаем
`ceiling`: лишний цвет безопаснее потери сюжета.

`KneeFactor = 3.5` — **консервативно** (меньше → раньше стоп → больше цветов →
безопаснее для сюжета; больше → рискованнее). По договорённости с мастером
калибруется позже отдельным прогоном по `samples/` с воротами глазами — не в этой
задаче.

### Лесенка картонов на лету

Всё в `MosaicGenerationService.Generate` до второго `CoherentMap.Settle`
(загрузка, раскладка, кроп, поле направлений, тесселяция, сэмплинг, сглаживание,
`ToneMap`, локальный контраст, первое квантование и первый `CoherentMap`) **не
зависит** от `MaxColors`/`PinnedArticles`; `EffectiveSeed` тоже (`DeriveSeed` их
не хеширует). От числа цветов зависит только хвост: редукция → второй
`CoherentMap` → геометрия → рендер → расход.

`Generate` считает префикс один раз, строит лесенку, выбирает колено и печёт
картоны + таблицы расхода для диапазона **авто ±5** (≈11 ступеней), зажатого в
`[4, colorsBefore] ∩ [пол, потолок]`. Веб кладёт их в ту же temp-папку
(`cartoon-c{n}.png`) и держит стрелки ◄► над картоном: в пределах печёного
диапазона — мгновенная подмена картинки и тела таблицы расхода из встроенного
JSON, без запроса на сервер; за пределами — кнопка «пересчитать с N» (полный
прогон, чтобы получить рабочую схему с номерами и легенду под новое число).

Авто-выбор — ступень по умолчанию, подпись «взял N из M». Поле `MaxColors` в форме
остаётся потолком; хинт меняется на «верхняя граница; система возьмёт меньше,
если сюжет не пострадает».

## Приёмка

1. `dotnet test` — прежние зелёные + новые `ReductionLadderTests`.
2. `dotnet run --project src/MosaicGenerator.Web`: `samples/gull.jpg`, 21×21,
   потолок 12 → картон с авто-числом, подпись «взял N из 12». Стрелки ◄►: картон
   и таблица расхода меняются мгновенно в пределах ±5, без перезагрузки. За
   пределами — «пересчитать», полный прогон, схема под новое число.
3. Прогон по всем `samples/` скриптом из `docs/redukciya-svyazka-plan.md` §2.4
   (`--colors 12`), размеры 21×21 / A4 / 40×40 (+ 60×60 на gull/human/dolphin):
   смотреть `autoColors` / `kneeRatio` в `metrics.csv` и **картоны глазами** —
   `human` 40×40 (бровь, глазница), `gull` 40×40 (клюв как пятно), `dolphin`
   40×40 (серая спина без бежевой полосы). Авто-выбор не должен ронять эти черты;
   если роняет — уменьшить `KneeFactor`.
4. Ворота (правило приёмки): `dominant`, `v4`, `uncuttable`, доля бордюра — не
   регресс. Картон авто-ступени байт-в-байт совпадает с отдельным `Generate` при
   `MaxColors = AutoColors` (доказать, что префикс/сид не поехал).

## Сделано 2026-09-07

Код написан по плану, `dotnet test` зелёный (+7 `ReductionLadderTests`), веб-поток
проверен end-to-end (стрелки, печёные `cartoon-c{n}.png`, подмена таблицы, `?c=`).

- `ReductionLadder` / `ReductionRung` / `ColorLadderPick`, `PaletteReducer.BuildLadder`,
  `Reduce` — тонкая обёртка над `BuildLadder(floor: maxColors)`. `CheapestToDrop` теперь
  отдаёт `out double` — стоимость сброшенного оттенка, это `MarginalCost` ступени.
- `MosaicGenerationService` разбит на `Prepare` (префикс → `Prepared`) и
  `RenderAt(ctx, rung, full)` (хвост). `Generate` строит лесенку до пола 4, берёт колено,
  печёт картоны + расход для `chosen ± 5 ∩ [пол, потолок] ∩ [2, colorsBefore]`.
  `MosaicGenerationOptions.BakeColorLadder` (по умолч. true) — стенд ставит false.
- `MosaicRequest.ForceColors` — точное число, ставится только кнопкой «пересчитать при N»
  за пределами печёного диапазона; в сид не хешируется.
- Веб: `StoredColorRung`, `IResultStore.Save` берёт словарь картонов,
  `ReadLadderCartoon`, `MosaicController.Cartoon(?c=)`, стрелки в `Result.cshtml` +
  `ui.js` (мгновенная подмена картона и тела таблицы расхода из встроенного JSON).
- Стенд: колонки `autoColors` / `kneeRatio` / `ceilingColors` в `metrics.csv`, в консоли
  `(авто N/M, колено R)`.

**Колено при `KneeFactor = 3.5` на реальных фото почти всегда возвращает потолок**
(gull/dolphin/human/landscape/sunset 21×21 и 40×40 — все `авто 12/12`, только poppy 21×21
дал 11/12). Причина: редукция со 152-цветной палитры начинается с двух-трёх почти нулевых
сбросов дублей-представителей, дальше любой сброс выглядит «дорогим» относительно
накопленной медианы, колено срабатывает сразу и зажимается потолком. Это ожидаемое
консервативное поведение (план: «лишний цвет безопаснее»), калибровка `KneeFactor` — и,
возможно, замена накопленной медианы на скользящее окно — отдельной задачей по `samples/`
с воротами глазами. Колонка `kneeRatio` (3,5–8,0 на прогоне) — сигнал для этой калибровки.

## Откат

`Reduce` остаётся обёрткой с прежней сигнатурой и поведением; чтобы вернуть
жёсткий лимит из формы — в `Generate` заменить `ladder.Knee(request.MaxColors)`
на `request.MaxColors` и не печь лесенку. Веб-часть (стрелки) при этом просто не
показывается.
